Autonomous Research Pipeline

Four agents — search, analyst, fact-check, and writer — cooperating through a shared task queue to turn a one-line topic into a sourced, structured research brief.

search_agent→ analyst_agent→ factcheck_agent→ writer_agent

The brief: produce a research memo good enough to open a strategy meeting with, from nothing but a topic string, in under five minutes, without a human touching a search bar.

Why a single agent wasn't enough

The first version of this was one agent with a search tool and a big system prompt telling it to "research thoroughly." It worked for shallow topics and fell apart on anything contested — it would settle on the first plausible-sounding source, present a single narrative as consensus, and never flag its own uncertainty. The failure wasn't the model; it was the design. One agent playing four roles at once has no natural point to disagree with itself.

Splitting the job into four agents with narrow, single-purpose responsibilities fixed most of this — not because any individual agent got smarter, but because the pipeline now has a structural place for verification to happen.

Core idea

Give each agent one job and one tool set. Let disagreement between agents — not confidence within one agent — be the thing that catches errors.

The architecture

The pipeline runs as an orchestrator pattern: a lightweight controller script passes a task object down the chain, and each agent reads from and appends to it rather than starting from scratch.

  • search_agent — takes the topic, generates 4–6 query variants, hits a search API, and deduplicates sources by domain and content similarity before passing along the top 10–15.
  • analyst_agent — reads the source set, clusters findings into themes, and explicitly tags where sources disagree instead of averaging the disagreement away.
  • factcheck_agent — takes only the analyst's specific factual claims (not the whole draft) and independently re-searches each one, flagging anything it can't verify from at least two sources.
  • writer_agent — assembles the final brief, and is instructed to keep flagged/unverified claims visibly marked rather than smoothing them into confident prose.
task = {
  "topic": input_topic,
  "sources": [],
  "themes": [],
  "flagged_claims": [],
  "draft": None
}

for agent in [search_agent, analyst_agent, factcheck_agent, writer_agent]:
    task = agent.run(task)

Simplified controller loop — production version adds retries, timeouts, and per-agent logging.

What broke, in order

1. The analyst agent laundered disagreement into consensus

Early on, when two sources conflicted, the analyst would just pick the more confidently-worded one and present it as fact. The fix wasn't a smarter prompt — it was changing the analyst's output schema to require a confidence and disagreement field per theme, so there was no valid output shape that let it skip the conflict.

2. The fact-checker re-trusted its own source

Giving the fact-check agent the same source list as the analyst meant it was "verifying" claims against the exact documents that produced them — a closed loop that verified nothing. The fix: the fact-checker gets the claim only, not the source, and has to search independently.

3. Silent tool failures

When the search API rate-limited, the search agent would quietly return an empty list and the pipeline would happily write a brief with zero sources. Now every agent validates its own output against a minimum bar (e.g. "at least 3 sources") and raises rather than passing along an empty result.

The most useful failure mode to design for isn't the wrong answer — it's the confident empty one.

Stack

  • Orchestration: a plain Python controller (no framework) — the pipeline is short enough that an agent framework added more indirection than it saved.
  • Models: a fast model for search-query generation and clustering, a stronger model reserved for the fact-check and writing steps.
  • Tools: web search API, a lightweight content-extraction step, and a JSON-schema validator between every agent handoff.

What I'd change next

The fact-check step currently runs sequentially after the full draft; running it earlier, per-claim, as the analyst produces them, would likely cut latency substantially. That's the next iteration — logged here once it ships.

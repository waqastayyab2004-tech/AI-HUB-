What Makes an Agent "Agentic"? A Practical Definition

The word gets applied to everything from a single chained prompt to a full multi-agent swarm. Here's the definition I actually build against.

"Agentic" has become a label people reach for whenever a system uses an LLM more than once. That's not a useful bar. A script that calls a model three times in a row isn't agentic just because it loops — it's still a script.

The definition I work from has three parts, and a system needs all three to earn the word:

  1. It decides its own next step. Not just which template to fill — which tool to call, in what order, based on what it just observed. If the control flow is fixed in advance, it's automation, not agency.
  2. It can act on the world, not just generate text. Search, write files, call an API, send a message. An agent without tool access is a chatbot with extra steps.
  3. It can recover from an unexpected result. A tool call fails, a page returns nothing, a sub-task's output doesn't match what was expected — an agentic system notices and adapts rather than plowing forward with garbage.
Working definition

An agent is a system that chooses its own actions, can act on the world through tools, and can adapt when those actions don't go as expected.

Why the distinction matters in practice

It's not pedantry — it changes what you build. If a workflow is genuinely fixed-order (step 2 always follows step 1, with no branching decision in between), building it as an "agent" adds cost and unpredictability for nothing. A plain script with an LLM call at the steps that need judgment will be cheaper, faster, and easier to debug than a general-purpose agent loop.

The reverse is just as common: teams hard-code a decision tree to avoid "agent unpredictability," and end up with a brittle script that breaks the moment reality doesn't match the tree. That's usually the sign the task actually needed an agent — something that can look at an unexpected result and decide what to do about it, instead of a maintainer adding another elif.

A quick test

Before calling something an agent, I ask: if I removed the model's ability to choose its next action, would the system still work the same way? If yes, it's automation with an LLM step. If no — if the choice of what happens next is genuinely load-bearing — it's agentic.

Agency isn't a feature you add. It's the amount of the decision you're willing to hand over.

Where multi-agent systems fit

Multiple agents aren't required for something to be agentic — a single agent with tools and judgment qualifies. Splitting work across agents (as in the research pipeline case study) is a design choice for a different reason: narrower responsibility per agent, and a structural point where one agent's output can be checked by another, rather than trusting a single agent to self-police everything at once.

End of note
